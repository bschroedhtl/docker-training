12  DB Containers / Persistent Volumes

Especially for hosting a database container, the data managed by the DBMS should survive a container life cycle.

This means, if someone shuts down the container with docker compose down or manually removes the database container with docker rm -f ..., we would like to see the same data after launching a new database container.

For this, we need to map the file path inside the db container, where all the database files are stored internally, to a volume, which persists independently of the container.

This file path depends on the DBMS, for instance for mysql it is /var/lib/mysql

12.1 Volume declaration

Similar to a service or network declaration, a volume declaration in a compose file looks like this:

volumes:
  data:
    name: mysql-data

In a terminal, the corresponding command would be docker volume create mysql-data. Compose creates the volume automatically, if it does not exist yet.

Docker-managed volumes can also be inspected and deleted manually:

  • docker volume ls
  • docker volume inspect mysql-data
  • docker volume rm mysql-data (be careful!)

12.2 Volume mapping for a mysql container

services:
  mysql:
    image: mysql:8.4
    container_name: dev_mysql
    environment:
      MYSQL_USER: user
      MYSQL_PASSWORD: user
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: userDB
    volumes:
      - data:/var/lib/mysql

With this volume mapping, the container internal path /var/lib/mysql is mapped to the docker-managed volume data (named mysql-data, according to the volume declaration above).

Note:

  • Still, you could map a local host path on the left side, by specifying a relative or absolute file path instead of the name of a volume.
  • This is called a bind mount, whereas mapping to a docker-managed volume is called a named volume.
  • In the first case, the files are accessible very easily, you can browse them in the local file system. But this is also more dangerous, since you could delete some files by accident.
  • In the second case, the files are managed by docker and stored in a part of the host file system which is managed by docker (/var/lib/docker/volumes/ on Linux, inside the Docker Desktop VM on Windows/macOS), so it is not easy at all to delete them by accident.

Refer to:

  • https://docs.docker.com/engine/storage/ (overview of volumes, bind mounts and tmpfs mounts)
  • https://docs.docker.com/engine/storage/volumes/

12.3 phpMyAdmin

With the DNS resolution inside a docker network, a good practice for database management in docker is to hide a DBMS docker container from the external world, while only neighbour containers inside the same docker network are able to contact this DBMS.

Note:

  • During development, you might still want to publish the database port, so you can inspect your tables with a database tool on your host (see exercise below).

We test this security feature by setting up a second container using the phpmyadmin image, which is basically a web server providing a user interface for browsing a relational database. This web service uses PHP to communicate with the DBMS container, and for this, network traffic inside the docker network is sufficient!

Note:

  • That’s the reason why the mysql container does not specify a port mapping, hence it is not reachable from outside!

12.3.1 pma Container

  phpmyadmin:
    image: phpmyadmin
    container_name: dev_pma
    environment:
      PMA_HOST: mysql
      PMA_PORT: 3306
      PMA_ARBITRARY: 1
    restart: always
    ports:
      - 8183:80

During startup of a phpMyAdmin container, this application refers to several environment variables. Those can easily be specified in a compose file:

  • PMA_HOST: Hostname or IP address of the DBMS which shall be browsed
  • PMA_PORT: By default, a mysql database listens on port 3306 for incoming client connections
  • PMA_ARBITRARY:
    • If set to 0, the web interface is fixed to the given PMA_HOST. In the login dialog, you are only asked for username and password.
    • If set to 1, the web interface is allowed to connect to arbitrary DBMS hosts. In the login dialog, you can also enter the PMA_HOST which shall be connected, in addition to username and password.

12.4 First Booting

If the compose file is started for the first time, mysql detects an empty data directory and creates the requested database and user (refer to environment variables passed to the mysql container).

Note:

  • These environment variables are only evaluated if the data directory is empty. Changing them later has no effect on an existing volume.

Since the docker-managed volume survives several downs and ups of the compose network, all data remain there, until someone manually deletes the volume in a terminal with docker volume rm mysql-data, or with docker compose down -v (which removes the containers together with the volumes declared in the compose file).

12.5 Exercise

12.5.1 Database hidden

  • Boot the compose network
    • On the very first start, MySQL needs some time (up to about a minute) to create the database. Until then, the login fails. Watch docker logs -f dev_mysql until you see ready for connections together with port: 3306 (stop watching with Ctrl+C). An earlier line with port: 0 belongs to a temporary setup server - keep waiting.
  • Test the web interface in your favourite browser : http://localhost:8183
    • Login with root/root or user/user
    • Test various host names in the Server field of the login dialog: mysql (service name), dev_mysql (container name), the IP address of the container (find it with docker network inspect backend) and localhost.
    • Why does localhost not work? (Hint: inside the phpMyAdmin container, localhost means the phpMyAdmin container itself.)
  • Create a new table with some columns
  • Shut down the network with docker compose down.
  • Boot again, login to the database in the browser and inspect the new table.

12.5.2 Database with external port mapping

  • Try to connect to the database from an external sql browser (like JetBrains DataGrip, HeidiSQL or similar) => should not be possible.
  • Change the compose file and add a port mapping for the mysql container (remove the # in the commented ports lines), then run docker compose up -d again.
    • If you get port is already allocated, another MySQL (e.g. from XAMPP) is running on your computer. Stop it, or use another host port, e.g. 3307:3306.
  • Try again to connect to the database from an external sql browser => should work now! (Host localhost, port 3306, user user, password user)
  • Clean up: docker compose down (the volume mysql-data stays; docker compose down -v deletes it too)

Note: Passwords written directly into a compose file are fine for a local development setup, but never for a real server.
